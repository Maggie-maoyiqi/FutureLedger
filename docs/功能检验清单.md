# FutureLedger 功能检验清单

> 更新说明（2026-11-01）：正式启动路径必须配置真实可用的 LLM；`local` provider 只用于自动化测试注入，不能作为用户启动模式。

这份清单对应当前仓库实际能够运行的功能。每个示范问题都给出了入口、预期结果和自动化检验位置。金额使用合成数据；不要输入真实账户、密码或 API key。

## 一、最容易直接演示的本地账本 Demo

启动：

```bash
python3 scripts/generate_data.py
python3 -m pip install -r requirements-demo.txt
export FUTURELEDGER_PROVIDER=deepseek  # 或 openai / compatible
export FUTURELEDGER_API_KEY='YOUR_APIKEY'
export FUTURELEDGER_MODEL='YOUR_MODEL_NAME'
python3 -m uvicorn --app-dir "$PWD" demo.api:create_app --factory --host 127.0.0.1 --port 8000
```

启动必须配置真实可用的 LLM provider、API key 和 model；应用不会使用 local offline mode。自动化测试会注入独立的 deterministic test provider，不代表用户启动时可以省略 LLM 配置。

真实 LLM 启动后的最小验证流程：

1. 用上面的环境变量和启动命令启动服务。
2. 注册并登录一个演示用户。
3. 输入 `8月和9月的各项净支出`，确认系统能把连续月份理解为完整日期范围，并按类别分组。
4. 输入 `给测试用户B转25元`，确认先进入密码确认流程，不会直接执行。
5. 输入 `我想存6000元买电脑，至少留3000元`，确认进入规划路由，不会直接转账。

如果启动阶段报 provider、API key 或 model 缺失，先检查三个 `export` 变量；这表示配置未通过启动校验，不是查询 SQL 的问题。

浏览器打开 `http://127.0.0.1:8000/`。首次使用先注册并登录 `test_user` 或 `isolation_user`，密码至少 12 个字符。

### 1. 登录、会话和个人数据隔离

- 输入：登录 `test_user`，然后查询“我的账户余额”。
- 预期：只返回当前用户自己的账户和流水；不能读取 `isolation_user` 的数据。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_scope_plan_and_sql_guards`。

### 2. 单值金额卡片

- 输入：`这个月的支出是多少？`
- 输入：`2026年9月餐饮净支出是多少？`
- 预期：返回一个金额卡片，不返回 SQL 或内部凭据。
- 图表类型：`metric_card`。

### 3. 收入、支出和退款口径

- 输入：`上个月的收入明细`
- 输入：`2026年9月餐饮净支出是多少？`
- 输入：`2026年9月退款是多少？`
- 预期：收入、消费支出和退款使用不同的固定指标口径；转出计入支出总额和确认时选择的用途类别，转入计入收入总额。

### 4. 类别、商户和账户分组

- 输入：`2026年9月各类别净支出排名前五`
- 输入：`2026年9月各商户支出`
- 输入：`2026年9月各账户支出`
- 预期：使用 `group_by`，返回多行统计结果；排名问题返回柱状图或有序表格。
- 图表类型：排名通常为 `bar`，普通分组为 `table`。

### 5. 月度趋势和多系列趋势

- 输入：`2026年每月餐饮净支出趋势`
- 输入：`最近三个月每月各类别净支出趋势`
- 预期：横轴是月份；不同类别是不同系列；月份缺失时仍按完整月份范围解释。
- 图表类型：`line`。

### 6. 明细和平均值

- 输入：`上个月餐饮平均每笔消费是多少？`
- 输入：`2026年9月餐饮消费明细`
- 输入：`本月转账记录`
- 预期：平均值返回明确的每笔口径；明细返回表格，不把内部 `transaction_id` 暴露在普通回答中。
- 图表类型：平均值为 `metric_card`，明细为 `table`。

### 7. 导出查询结果

- 先输入：`2026年9月餐饮净支出是多少？`
- 再点击结果中的 CSV 下载。
- 预期：只有当前 session 可以下载自己的查询结果；换另一个用户的 session 会被拒绝。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_export_is_session_scoped`。

### 8. 澄清和追问

- 输入：`2026年9月各类别排名前五`
- 预期：系统先询问排名指标。
- 继续输入：`按净支出`。
- 预期：系统沿用上一轮问题并返回净支出排名。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_clarification_followup_keeps_dataset_and_prior_question`。

### 9. 路由、普通对话和规划识别

- 输入：`你好`
- 输入：`这个月的支出是多少？`
- 输入：`给测试用户B转25元`
- 输入：`我想存6000元买电脑，至少留3000元`
- 预期：分别进入普通回答、查询、执行确认、规划四类路径。
- 规划请求返回带假设的确定性方案比较，不会直接转账，也不会把全部流水发送给模型。

### 10. 演示转账

- 输入：`给测试用户B转25元`
- 预期：先返回转账预览，不能直接扣款。
- 输入错误密码：应返回验证失败，余额不变。
- 输入正确密码后选择 `购物` 并确认：转出方增加一笔 `transfer/OUT`，同时计入“支出总额”和“购物”类别；转入方增加一笔 `transfer/IN` 并计入收入，双方余额同步更新。
- 预期：重复提交同一个 action 不会重复扣款。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_transfer_requires_password_then_category_and_counts_as_inflow_outflow`。

### 11. 现金流规划模拟

- 输入：`我想存6000元买电脑，至少留3000元`
- 预期：聊天入口提取并校验目标和保留余额，缺参时追问；完整参数调用确定性模拟，返回比较卡片和曲线，不会自动执行转账。
- 模拟接口：`POST /api/plans/{plan_id}/simulate`，请求体至少包含 `session_id`、`plan_version`、`salary_day`、`purchase_day`、`daily_budget_cents`、`floor_cents`、`goal_cents`。
- 预期：返回逐日余额、最低余额、最低日期、可行性、事件和假设；不修改账本流水。
- 检验：`tests/test_part_d.py` 中的 cashflow/API 测试。

## 二、查询安全和模型调用

### 12. IntentPlan 和只读 SQL

- 输入：`DROP TABLE transactions`
- 输入：`删除所有流水`
- 预期：返回 `blocked`，不会执行 SQL。
- 输入：正常查询时，模型只生成结构化 IntentPlan；后端根据语义目录编译只读 SQL。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_scope_plan_and_sql_guards`。

### 13. 未知类别、未知商户和越权账户

- 输入：`2026年9月不存在的类别支出`
- 输入：要求查询另一个用户的账户。
- 预期：返回澄清或拒绝，不能悄悄删掉过滤条件后返回总数。

### 14. LLM 兼容性

- 配置 DeepSeek：`FUTURELEDGER_PROVIDER=deepseek`、`FUTURELEDGER_API_KEY=YOUR_APIKEY`、`FUTURELEDGER_MODEL=YOUR_MODEL_NAME`。
- 配置 OpenAI-compatible 服务：额外设置 `FUTURELEDGER_API_BASE=https://provider.example/v1`。
- 输入：`8月和9月的各项净支出`。
- 预期：模型理解省略年份和“各项”的分组含义，输出合法 IntentPlan；最终查询仍由后端执行。
- 检验：`tests/test_text2sql_demo.py::DemoTest::test_model_infers_year_and_grouping_from_meaning_with_current_date_context` 以及 Provider 测试。

## 三、B/C Agent API 和 Role A 模拟银行

以下功能不是默认的简单 `demo.api` 页面，而是独立服务。它们需要按各自 README 启动，并使用合成数据。

### 15. B 安全执行门

- 操作：创建转账操作 → 确认参数和 `params_hash` → 高风险操作输入密码 → 提交。
- 预期：服务端计算风险等级和日额度；模型或浏览器不能自行提高额度；重复幂等键只产生一次扣款。
- 故障问题：银行已经成功但响应丢失时，状态为 `PENDING_UNKNOWN`，必须查证，不能直接重试付款。
- 检验：`tests/test_execution_gate.py`、`tests/test_b_c_adapter.py`。

### 16. A 模拟银行读接口

- 操作：查询账户余额、收款人、流水和 mandate。
- 预期：请求同时需要内部服务 token 和当前用户主体；不能跨用户读取。
- 示例：

```bash
curl -H "Authorization: Bearer $FUTURELEDGER_INTERNAL_TOKEN" \
  -H 'X-Authenticated-User: test_user' \
  http://127.0.0.1:8001/bank/v1/accounts/acc_daily/balance
```

### 17. A 模拟银行转账和对账

- 操作：报价 → 提交 500 元转账 → 查询状态 → 运行 reconciliation。
- 预期：余额、transfer、POSTED 流水和两腿 journal 在同一事务中保持平衡；相同幂等键重放不会二次扣款。
- 检验：A 模块安装 pytest 后运行 `services/mock-bank/README.md` 的验证命令。

### 18. A/B 连接

- 配置：在 C/B dev app 中设置 `FUTURELEDGER_BANK_URL` 和 `FUTURELEDGER_BANK_TOKEN`。
- 输入：通过 Agent API 提交转账提议。
- 预期：C 只负责意图和编排，B 负责确认/验证/Outbox，A 负责最终余额和流水事实。
- 检验：`tests/test_a_b_adapter.py`、`tests/test_b_c_adapter.py`。

## 四、当前明确未完成的范围

- `apps/web/` 的 Vue 3 工作台已接入现有 Demo API，可用于桌面浏览器演示；移动端适配、完整业务页面和生产认证仍属于后续工作。
- 本地 demo 登录是演示认证，不是生产身份系统。
- A/B 适配器在配置持久 `FUTURELEDGER_EXECUTION_DB` 时保存原主体和幂等键，支持丢失回包后重启查证；C 的会话、DAG 和 SSE 仍未持久化。未来日期转账尚未支持，会明确拒绝。
- A 模拟银行依赖 PostgreSQL、Docker、Conda 和 pytest；默认 Text2SQL demo 仍必须配置 LLM，但不依赖 A 的 PostgreSQL。
