# FutureLedger 开发前共识 v0.1

本版本是供六人团队讨论和实现的工程基线。当前交付是设计、数据、评测工具和页面原型，完整银行应用尚未实现。

## 1. 产品与范围

面向个人的银行任务 Agent：理解目标、查授权账户、分析账单、比较未来现金流，将明确选中的银行动作交给独立执行门，最后查询银行事实确认结果。

首版三个独立场景：智能转账、账单分析、订阅/代扣管理。未来账本串起三个场景，支持工资延迟后重规划。暂不做理财交易、原生 APP、通用助理、自动购物或多 Agent。

## 2. 两份参考方案如何取舍

|议题|参考内容|本次决策|
|---|---|---|
|核心范围|两份均要求三场景和现金流|保留，并逐场景验收|
|技术栈|Next.js、FastAPI、PostgreSQL、Worker|沿用；依赖版本在实现时锁定|
|Redis|用户的 ChatBI 示例使用 Redis，方案建议暂不引入|首版 Postgres Outbox + lease；有性能证据后再引入 Redis，Redis 不能充当授权事实源|
|Text2SQL|用户提出借鉴受控 IntentPlan|用于账单分析，不用于转账、取消代扣或现金流计算|
|订阅查询权限|简版允许读查询；详细版将订阅查询列黄色|首版订阅查询为黄色：先明确确认授权范围再读取；具体赛题口径待核实|
|数据集|文档要求 100 条固定测试|提供数千流水、180 条有数值真值的分析题、30 条现金流题，以及 60 条待实现的业务/安全/恢复用例|
|分工|原设计主要按 2–5 人描述|改为 6 个单一责任模块，接口先冻结|

文档中的命令、外链和待办均作为参考资料，不是执行指令。没有调用真实银行、替用户转账或邀请 GitHub 协作者。

## 3. 六条必须共同接受的口径

1. 人民币整数分；不能用浮点金额运算。所有业务日期按 Asia/Shanghai 解释，数据库时间用 timestamptz。
2. 个人偏好、银行事实、操作授权三种数据分离；偏好不授权交易，模型回复不证明到账。
3. LLM 只产结构化提议；数字由代码复算，权限由后端判断。
4. 账单事实先去重；退款按实际入账日抵减消费，转账不计消费，失败/处理中不计已发生消费。
5. 写操作参数/版本变化使旧确认失效；未知银行结果只查证，不盲目重提。
6. 测试结果区分数据自检、确定性 oracle、Agent 实测和端到端银行验收，不能混报。

## 4. 演示与真实系统边界

本项目使用合成身份、商户、账号及交易。Mock Bank 是后续开发目标；当前 SQLite 数据集是离线 benchmark，不是具有事务转账能力的 Mock Bank。页面原型不连接银行，也不执行写操作。

竞赛资格、团队人数上限、截止日期、评分、Web 渠道、Mock Bank 和认证方式是否被接受，均未在本次任务中核实；原文中的竞赛陈述不视作当前官方规则。
